# OpenAI's Responses API Streams a Whole Item Lifecycle, Not Just Deltas

If you've only streamed Chat Completions before, the Responses API's event stream is a different shape entirely. Chat Completions gives you a flat sequence of token deltas. Responses gives you a stateful lifecycle: `response.output_item.added` introduces an item at a given `output_index`, `response.content_part.added` opens a content part inside it at a `content_index`, then `response.output_text.delta` events reference *both* indices — and everything is threaded together by a `sequence_number` that's supposed to strictly increase across the entire stream. Reasoning items, function calls, MCP tool calls, and built-in tools like code interpreter and web search each get their own event families layered on top of the same lifecycle.

That's a lot more structure than Chat Completions ever asked you to track, and the moment you're not consuming the stream through the official SDK end-to-end — proxying it through your own backend, re-serializing it in another language, buffering it through a queue — it's easy to drop the `output_item.added` event and keep every delta after it, or let a re-ordering step scramble `sequence_number`. None of that raises an error on your side. A real client either silently drops the content or renders it against the wrong item, and you find out from a confused screenshot, not a stack trace.

I pulled the exact event schemas straight from the `openai` npm package's own TypeScript definitions — the same `ResponseStreamEvent` union the official SDK is generated from — rather than working from a docs summary, and built a validator covering all 58 currently documented streaming event types. Paste a raw SSE response and it checks required fields per event, flags a delta whose `item_id` was never introduced by an `output_item.added`, catches a content part used before its `content_part.added`, flags items that never get closed with `output_item.done`, and checks that `sequence_number` actually increases. It also reconstructs the final output — text, reasoning summary, function-call arguments — so you can see what a real client would have rendered.
