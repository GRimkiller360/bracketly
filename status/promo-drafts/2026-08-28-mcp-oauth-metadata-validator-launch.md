# Your MCP Client's client_id Is Now a URL — and It Has to Match Exactly

If you built an MCP client any time before this year, registering it with an authorization server meant Dynamic Client Registration: a POST to a registration endpoint, and the server hands you back a `client_id` and (often) a secret. That flow is now deprecated. MCP's 2026-07-28 spec formally deprecated RFC 7591 DCR, keeping it around only for backward compatibility, in favor of Client ID Metadata Documents — a scheme where you host a static JSON file yourself, and the URL you host it at *is* your client_id. No registration step, no secret, no server-side account to manage.

It's simpler in theory. In practice, the failure mode is brutal: get one detail wrong, and the authorization server just rejects your client with an opaque error that gives you no hint the metadata document is the problem.

The gotcha that stood out most while building this: the authorization server checks your `client_id` against the URL it fetched the document from using a *plain string comparison* — not a normalized URL comparison. A trailing slash on one side and not the other, a different case in the hostname, an explicit `:443` your code adds but your document omits — any of those breaks it silently. There's no error message pointing at "URL normalization mismatch"; you just get rejected.

The other rules compound from there. `redirect_uris` has real scheme constraints: HTTPS is always fine, plain HTTP is only allowed for a loopback address, and a custom scheme like `myapp://callback` is only valid if you've declared `application_type: "native"` — miss that field and a perfectly reasonable native-app redirect URI reads as invalid. `token_endpoint_auth_method` defaults to `client_secret_basic` in the base OAuth spec, which makes no sense here — there was never a registration step to issue you a secret — so it needs to be set explicitly to `"none"`. And if you're using `private_key_jwt` instead, it's worth double-checking your `jwks` doesn't contain a `d` member: that's the private key component, and a jwks meant to be published publicly should only ever carry public keys.

There's a companion problem on the resource-server side: Protected Resource Metadata discovery. Given a resource at `https://server.example.com/mcp`, the metadata document doesn't live at `.../mcp/.well-known/oauth-protected-resource` — the well-known segment gets inserted *between* the origin and the path, landing at `https://server.example.com/.well-known/oauth-protected-resource/mcp`. It's a small detail, but it's broken in the wild across more than one real MCP implementation.

I couldn't find an existing free tool that checks any of this — paste-in web validators exist for other parts of the MCP ecosystem, but not for CIMD or PRM discovery. So: paste a Client ID Metadata Document (with an optional "hosting URL" field to check the exact-match rule), a Protected Resource Metadata document, a bare resource URL to get the correct discovery URL computed for you, or even a raw `WWW-Authenticate` header value to pull the `resource_metadata` URL out of it.
