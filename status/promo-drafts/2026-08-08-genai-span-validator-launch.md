# Your OpenTelemetry GenAI Spans Are Probably Still Using the Old Attribute Names

OpenTelemetry's GenAI Semantic Conventions — the standard attribute names for representing an LLM call, an agent step, or a tool execution as a regular span — have been under active development since 2024, and a few of the core attributes have already been renamed once. `gen_ai.system` became `gen_ai.provider.name`. `gen_ai.prompt` and `gen_ai.completion` were replaced by structured message attributes (and, more recently, the Events API). `gen_ai.usage.prompt_tokens`/`completion_tokens` became `gen_ai.usage.input_tokens`/`output_tokens`. None of this is exotic or hidden — it's all in the public registry — but it means any instrumentation written against an earlier draft, a tutorial that hasn't been updated since, or a hand-rolled OTel exporter can still be quietly emitting the deprecated names. The spans still show up. They just don't line up with what any current dashboard or observability vendor is keying off of.

I went looking for a free, no-install way to paste a span and check it against the current conventions, and came up mostly empty — the official tooling is [OTel Weaver](https://github.com/open-telemetry/semantic-conventions-genai), a Rust CLI that validates against the full schema, which is the right tool if you're maintaining an instrumentation library but overkill if you just want to sanity-check one span you're staring at in a trace viewer.

So I added a free [OTel GenAI Span Validator](https://bracketly.pages.dev/tools/genai-span-validator/) to Bracketly, my free client-side dev tools site. Paste a span's attributes — a flat object, a `{name, attributes}` span, an array of spans, or a full OTLP JSON export with the `resourceSpans → scopeSpans → spans` structure — and it checks that `gen_ai.operation.name` and `gen_ai.provider.name` are present (the two attributes required on every GenAI span), flags any of the deprecated attributes above with their current replacement, type-checks the numeric/boolean/array-valued attributes (token counts, temperature, stop sequences), validates the enum fields, and checks the span's name against the spec's own naming convention — `{operation.name} {model}` for inference and embeddings spans, `{operation.name} {data_source.id}` for retrieval, or just the bare operation name for agent and tool spans.

Everything is checked directly against the current OpenTelemetry GenAI attribute registry and span-naming documentation, not from memory — and since the spec is still evolving, an operation or provider name this checker doesn't recognize is flagged as a note to double-check rather than a hard failure, since it might just be newer than the checker itself.

Like every tool on the site, it's 100% client-side — nothing you paste is sent anywhere. If you're instrumenting an LLM or agent app with OpenTelemetry, it's a fast first pass before reaching for the full Weaver toolchain.
